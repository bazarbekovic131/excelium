# Чек-листы на стороне Doc-V

Вся Doc-V-часть выполняется администратором. Сервис развёрнут на 25353 (deploy/README-deploy.md).

## Токен
1. Сгенерировать GW_TOKEN_DOCV, вписать в .env шлюза, перезапустить программу.
2. В карточке НАСТРОЙКИ завести Настроечное поле «Токен шлюза» и скопировать туда сгенерированное значение. Добавлять поле в HTTP-заголовки.

## 1. Переключение реестров

Старые URL были заменены на новые:

| Тип, точка | Было | Стало |
|---|---|---|
| Реестр платежей, «Отправка данных (внутренний реестр)» | :25351/form_inner_registry | :25353/render/registry/inner |
| Реестр платежей, «Отправка данных (внешний реестр)» | :25351/form_outer_registry | :25353/render/registry/outer |
| Реестр предстоящих платежей, «Отправка данных (реестр предстоящих платежей)» | :25351/form_priority_registry | :25353/render/registry/priority |

В каждом действии добавлены HTTP-заголовки: название `Authorization`, значение из поля «Токен шлюза» НАСТРОЕК с приставкой `Bearer `

Тело и разбор ответа не меняются: тот же JSON, в ответе тот же `download_url`. Скачивание файла по URL из поля работает как раньше (GET /files/* токена не требует).

## 2. Точка опроса очереди (веха M5) — тип «Шлюз»

1. Служебный тип документа «Шлюз», один документ, доступ только админам.
2. Точка «Опрос», на неё — действия по порядку:
   1) «HTTP-запрос»: GET `http://192.168.30.19:25353/jobs/pending?consumer=docv&limit=20`,
      заголовок Authorization как выше, ответ в JSON-поле «Задания».
   2) «Условие»: «Задания» пусто или `[]` -> стоп (эта ветка срабатывает
      в 99% прогонов, после неё не должно быть ни одного действия).
   3) Разбор: для каждого задания — «Выборка» по полю «job_id» среди уже
      созданных документов (дедуп), затем «Создание» из JSON; в создаваемый
      документ обязательно инициализировать поле с job_id.
   4) «HTTP-запрос»: POST `.../jobs/ack`, тело `{"ids": [...]}` из поля.
3. Планировщик задач: запуск точки «Опрос» каждые 30 секунд.
   ВАЖНО: интервал живёт в серверном «Планировщике задач» и НЕ попадает
   в экспорт конфигурации — зафиксировать в вики.
4. Продюсерам (1С и др.) выдать их токены (GW_PRODUCER_TOKENS в .env)

## 3. Операции /ops (веха M4)

Токен GW_TOKEN_OPS — отдельный, тоже в НАСТРОЙКИ (отдельное поле).
Вызов: «HTTP-запрос» POST `http://192.168.30.19:25353/ops/<имя>`,
тело — JSON-поле вида `{"params": {...}}`, ответ в JSON-поле; успех
проверять условием по `ok`, а не по коду HTTP (он всегда 200).
Список операций: GET /ops. Порождённые файлы приходят в `files[]`
ссылками download_url.

## 4. Подписанты: состав знает шлюз

Doc-V подписи не присылает и не должен: в теле запроса их нет. Шлюз сам
знает, кто подписывает реестр этой компании, и пишет в Excel готовые
строки — ни номеров строк, ни VLOOKUP, ни скрытых листов СПР в выдаче.
Выпущенный реестр больше не меняется задним числом.

Источников правды два, и они не пересекаются:

- **Люди — Структура Doc-V.** Кто существует, как зовут, uid. Своего
  списка людей у шлюза нет. Выгрузка приходит действием «HTTP-запрос»
  POST `/directory/structura`, тело — массив с ключами `uid`,
  `display_name`, `position`, `department`. Хвост «(Должность)» из
  `display_name` в подпись не идёт.
- **Должности шлюза** — в каком качестве человек подписывает. У
  должности ключ, печатаемое название и кто занимает — сотрудник из
  Структуры. **У должности ровно один человек**: подпись в реестре — одна
  строка, один человек. Если печатаемое название общее, а люди разные,
  это разные должности с одинаковым названием: «Гендиректор
  Шар-Құрылыс» и «Гендиректор дочерних» обе печатаются как «Генеральный
  директор». Кого в Структуре нет, вписывается в должность одним полем
  ФИО.

Правила компаний и наборы согласующих ссылаются только на должности.
Своё у них одно — компания в подписи. Смена подписанта делается в
одном месте: у должности меняется человек, и это доходит до всех
реестров сразу.

Раздел «Подписанты» — три вкладки: компании, наборы согласующих,
должности. Списки правятся целиком: строки добавляются и убираются на
месте, сохранение одно на весь список.

### Компании и правила

Правило — компания, объект (пусто — вся компания), набор согласующих и
две верхние подписи: СОГЛАСОВАНО слева, УТВЕРЖДАЮ справа. Объект без
своей верхней подписи берёт её из правила компании. Названия
организаций сравниваются нестрого: кавычки, хвост «(KZT)», казахские
буквы против русских похожих и лишние пробелы на подбор не влияют. Не
нашли правила — в журнале предупреждение с компанией и объектом,
реестр выходит без подписей.

Утверждающий у компании один на все объекты, поэтому у компании есть
форма «Проставить во все правила»: флажок у поля решает, менять его или
оставить.

### Наборы согласующих

Подписи под таблицей, по порядку. У строки — должность, компания в
подписи, заголовок над подписью («СОГЛАСОВАНО») и виды затрат, при
которых строка не печатается.

### Выключатели вместо удаления

Три уровня, и все без удаления данных:

- **строка набора** — колонка «Печатать»: строка остаётся на месте, но в
  реестр не идёт;
- **должность целиком** — «в отпуске»: должность остаётся во всех
  правилах и наборах, но нигде не подписывает; у объекта подпись
  уступает правилу компании, а если и там она отключена — не печатается;
- **правило** — отключённое правило объекта уступает правилу компании,
  отключённое правило компании — как будто его нет.

Во всех трёх таблицах строки выбираются флажками; над таблицей
появляется панель: отключить, включить, удалить. У компании панель
умеет ещё «проставить отмеченное в выбранные» — то же, что форма
«Проставить в правила компании», но только для отмеченных строк.
Удаление должности, на которую ссылаются подписи, по-прежнему
не проходит — панель перечисляет пропущенные.

Вакантная должность (никто не назначен) в реестр не попадает: строка
просто выпадает, верхний блок остаётся пустым.

### Экспорт и импорт

Внизу вкладки «Компании» — «Скачать JSON»: весь состав одним файлом
(должности, наборы, правила, флаги). «Заменить из файла» стирает состав
и загружает его из файла; перед этим текущее состояние ложится в Файлы
закреплённой резервной копией `signers_backup_….json`. Слияния нет:
только полная замена.

### Первичное наполнение и перенос

При первом запуске с пустой базой состав переносится из прежних
источников: 113 правил, 9 наборов и должности по каждой паре
«должность + человек» старого справочника. Одиннадцать генеральных
директоров становятся одиннадцатью должностями с одним названием.
Печатается то же, что печатал VLOOKUP, — это проверяется тестом
построчно.

База прошлой недели, где были отдельные люди и четыре способа указать
подписанта, переносится на должности сама при старте; старые таблицы
после переноса удаляются. Если где-то была выбрана «должность
Структуры», после переноса подпись закреплена за тем, кто занимал её
на момент переноса.

Кнопка «Сопоставить по ФИО» на вкладке «Должности» подбирает
сотрудников Структуры для должностей, где человек вписан только
именем: по фамилии с инициалами. Остальных выбирайте из списка руками.

### Спросить у шлюза

Doc-V может получить состав подписей и для своих нужд — например,
чтобы напечатать карточку договора или показать состав в карточке
реестра:

```
GET http://192.168.30.19:25353/signers?company={{Организация}}&object={{Объект}}
```

Ответ: `soglasovano`, `utverzhdayu`, `coordinators` — у каждого `fio`,
`position`, `company`. Без параметра `company` возвращается список всех
привязок. Заголовок Authorization как обычно.

### Файл одним действием (без второго запроса)

В «HTTP-запросе» галка «загрузить файл» есть только у GET, а тело
JSON — только у POST. Чтобы не делать два действия, шлюз принимает
данные прямо в адресе и отвечает **самим файлом**:

```
GET http://192.168.30.19:25353/render/typst/contract_card?data={{JSON поле}}
GET http://192.168.30.19:25353/render/registry/inner?data={{JSON поле}}
```

Настройка действия: метод **GET**, URL шаблоном с подстановкой
JSON-поля в параметр `data`, переключатель **«Кодировка параметров в
application/x-www-form-urlencoded» включён** (иначе кавычки и кириллица
поедут), заголовок Authorization как обычно, переключатель **«загрузить
файл» включён**, результат — файловое поле с методом добавления файла.
Второе действие и разбор `download_url` не нужны.

Длина адреса: проверено до 37 000 знаков (200 согласований) — работает;
реальная карточка договора с девятью визами укладывается в ~4 600
знаков. Если данных станет заметно больше, вернитесь к паре запросов
POST + GET, как в реестре платежей.

Тем, кто ходит POST-ом и хочет файл в ответе вместо ссылки, достаточно
добавить `?direct=1`.

Отдельная печатная форма карточки договора:
`POST /render/typst/contract_card` (бывш. list_soglasovaniya —
переименован, ваши правки перенесены автоматически) — формат данных в
шапке самого шаблона (правится в /ui, вкладка «Шаблоны»). Оформление — по дизайн-системе «Приёмка ERP SHARK». Организация
передаётся объектом: `"organization": {"name": …, "code": "СМ",
"blank_filepath": "blank_sm.png", "top_margin": 4.2}`. Бланк ищется в
«Картинках» шлюза по имени файла (путь режется до имени, ключ
`blank_file_name` тоже принимается); `top_margin` — отступ в см под
шапку бланка. Коды поля «Виза» печатаются подписями: 1 — Согласен,
2 — Подписан, −1 — Не согласен, −2 — Не подписан; незнакомый код
выводится как есть. Строки группируются по первой колонке «Таблицы
решения» с подписью из `stage_label` (по умолчанию «ЭТАП», пустая
строка отключает группировку). Поле `qr` (адрес карточки документа)
шлюз сам превращает в QR-код;
код подлинности и время формирования шлюз добавляет автоматически
(GW_VERIFY_SECRET в .env). Если сервис уже запускался со старой версией
шаблона, новая из файлов сама не заедет: удалите шаблон в /ui →
«Шаблоны» и перезапустите юнит — засев подтянет свежий файл.

### Фирменные бланки

Печатная форма умеет ложиться на фирменный бланк компании: PNG бланка
подкладывается фоном всей страницы, текст печатается поверх между
шапкой и нижней лентой. Подготовка (раз на компанию):

1. Загрузите PDF или DOCX бланка на страницу «Файлы» в /ui.
2. Запустите операцию blank_to_png (страница «Операции») — получите
   blank.png первой страницы (DOCX-вариант требует libreoffice на
   сервере, PDF конвертируется всегда).

   ВАЖНО про DOCX: LibreOffice воспроизводит вёрстку Word близко, но не
   на 100% — плавающие текстбоксы и WordArt могут съехать на строку.
   Эталонный путь: открыть бланк в самом Word на любой офисной машине,
   «Сохранить как PDF», и конвертировать уже PDF — растеризация PDF
   ничего не искажает. Если PDF взять негде, поставьте на сервер
   метрически совместимые шрифты (`apt install ttf-mscorefonts-installer
   fonts-liberation && fc-cache -f`) — чаще всего смещение уходит.
3. Скачайте PNG и загрузите его в «Картинки» вкладки «Шаблоны» под
   именем по договорённости: `blank_<код>.png` (blank_shar.png).
4. В данные листа кладите `"org": {"blank": "blank_shar.png",
   "top_margin": 4.2}` — отступ в сантиметрах под шапку конкретного
   бланка подберите пробным рендером.

### Справочники соответствий (расшифровка UID)

Сериализация табличных полей отдаёт ссылки сырыми UID-ами
(«approved_by» в листе согласования). Шлюз расшифровывает их своими
справочниками: `POST /directory/structura` и `POST /directory/dolzhnosti`
(токен docv), тело — `{"items": [{"uid": "…", "display_name": "…", "position": "…",
"department": "…"}]}` (display_name нормализуется в name; position
текстом покрывает и должность в разборе — отдельный справочник
должностей не обязателен); каждый POST замещает справочник целиком. Рендер подкладывает справочники
каждому шаблону входом `sys.inputs.dir`; неизвестный UID печатается
укороченным («8 знаков…?»), коды визы (1/-1/2/-2) и ISO-даты шаблон
переводит сам.

Минимизация: выгружайте только участников согласований (фильтр цикла
по ролям «Подписант»/«Согласующий» Структуры) и только пары uid+name —
ничего сверх. Справочник, не обновлявшийся 30 дней, шлюз вычищает сам;
файл базы — с правами 600.

Выгрузка из Doc-V — точка на планировщике (раз в сутки) или кнопка
в НАСТРОЙКАХ: цикл replay по записям Структуры → add_key с arrayAction
собирает [{uid, name}] (uid — сырое значение ссылки, name —
отображаемое имя) → «HTTP-запрос» POST на /directory/structura;
вторая такая же цепочка по Должностям. Проверка: GET /directory
показывает счётчики.

## 4.1. Журнал событий, история операций, файлы

- **Журнал** — вкладка в шапке. Всё, что делали шлюз, Doc-V и
  администраторы: отказы, запуски, правки. Поиск по тексту, фильтр по
  окраске (отказы, сбои, работа, действия в панели), по типу события и
  периоду. Файл `var/audit.log` ротируется по размеру самим процессом
  (5 МБ × 5 частей); страница читает все части. Внешний logrotate для
  этого файла настраивать не нужно.
- **История операций** — на странице «Операции» внизу список запусков,
  у каждой операции — её последний запуск. После запуска открывается
  карточка запуска: параметры, вывод, файлы; «Повторить» запускает с теми
  же параметрами, «Открыть форму» подставляет их для правки. Запуски по
  API тоже записываются с пометкой источника. Хранится 30 дней, не
  больше 500 записей.
- **Файлы** — закреплённый файл (кнопка-булавка) переживает срок
  хранения: бланки, эталоны, резервные копии. Выбранные файлы
  удаляются, закрепляются и скачиваются архивом разом.

templates/typst/ — только начальный засев: новый файл импортируется
