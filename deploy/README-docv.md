# Чек-листы на стороне Doc-V

Вся Doc-V-часть выполняется администратором руками. Сервис при этом уже
развёрнут на 25353 (deploy/README-deploy.md), старый на 25351 живёт до
конца переключения.

## 0. Токены (один раз, до переключения)

1. Сгенерировать GW_TOKEN_DOCV, вписать в .env шлюза, перезапустить юнит.
2. В карточке НАСТРОЙКИ завести setting-поле «Токен шлюза» и вписать туда
   то же значение. Действия будут подставлять его в заголовок из поля.

## 0.1. Справочник подписантов на сервере (обязательно до переключения)

Матрица правится в `utils/firmen_und_objekte.py` (в git не хранится), а
шлюз читает собранный из неё `data/approvers.yaml`. После любой правки
матрицы:

    python3 scripts/approvers_from_py.py > data/approvers.yaml
    sudo systemctl restart docv-gateway

Если этого не сделать, реестр уйдёт со старым составом подписантов.
Шлюз пишет об этом warning при старте, когда матрица свежее справочника.

## 0.2. Сверка со старым сервисом (на реальном реестре)

Сохранить настоящий payload из Doc-V в файл и прогнать:

    python3 scripts/parity_check.py /tmp/real.json

Скрипт формирует реестр обоими способами и сравнивает ячейка в ячейку по
всем листам (время генерации пропускается). «совпадает» по нужному виду
реестра — можно переключать действие. Внешний реестр в старом сервисе
не работает вовсе (неверный путь к шаблону), поэтому по нему сверять
не с чем: проверяется глазами.

## 1. Переключение реестров (веха M2) — 4 действия «HTTP-запрос»

По одному, с наблюдением после каждого. Старые URL -> новые:

| Тип, точка | Было | Стало |
|---|---|---|
| Реестр платежей, «Отправка данных (внутренний реестр)» | :25351/form_inner_registry | :25353/render/registry/inner |
| Реестр платежей, «Отправка данных (внешний реестр)» | :25351/form_outer_registry | :25353/render/registry/outer |
| Реестр платежей, «Отправка данных (реестр предстоящих платежей)» | :25351/form_priority_registry | :25353/render/registry/priority |
| Реестр предстоящих платежей, «Отправка данных (реестр предстоящих платежей)» | :25351/form_priority_registry | :25353/render/registry/priority |

В каждом действии добавить HTTP-заголовок: название `Authorization`,
значение из поля «Токен шлюза» НАСТРОЕК с приставкой `Bearer ` —
если редактор заголовков не умеет «Bearer + поле», завести в НАСТРОЙКАХ
поле сразу со значением `Bearer <токен>`.

Тело и разбор ответа не меняются: тот же JSON, в ответе тот же
`download_url`. Скачивание файла по URL из поля работает как раньше
(GET /files/* токена не требует).

Откат любого шага — вернуть старый URL: старый сервис живёт.

## 2. Точка опроса очереди (веха M5) — тип «Шлюз»

1. Служебный тип документа «Шлюз», один документ, доступ только админам.
2. Точка «Опрос», на неё — действия по порядку:
   1) «HTTP-запрос»: GET `http://192.168.30.19:25353/jobs/pending?consumer=docv&limit=20`,
      заголовок Authorization как выше, ответ в JSON-поле «Задания».
   2) «Условие»: «Задания» пусто или `[]` -> стоп (эта ветка срабатывает
      в 99% прогонов, после неё не должно быть ни одного действия).
   3) Разбор: для каждого задания — «Выборка» по полю «job_id» среди уже
      созданных документов (дедуп), затем «Создание» из JSON; в создаваемый
      документ обязательно инициализировать поле с job_id.
   4) «HTTP-запрос»: POST `.../jobs/ack`, тело `{"ids": [...]}` из поля.
3. Планировщик задач: запуск точки «Опрос» каждые 30 секунд.
   ВАЖНО: интервал живёт в серверном «Планировщике задач» и НЕ попадает
   в экспорт конфигурации — зафиксировать в вики.
4. Продюсерам (1С и др.) выдать их токены (GW_PRODUCER_TOKENS в .env).

Семантика: at-least-once. Если ack не дошёл, задание выдастся повторно
через 60 с — дубль обязан гаситься выборкой из шага 3.

## 3. Операции /ops (веха M4)

Токен GW_TOKEN_OPS — отдельный, тоже в НАСТРОЙКИ (отдельное поле).
Вызов: «HTTP-запрос» POST `http://192.168.30.19:25353/ops/<имя>`,
тело — JSON-поле вида `{"params": {...}}`, ответ в JSON-поле; успех
проверять условием по `ok`, а не по коду HTTP (он всегда 200).
Список операций: GET /ops. Порождённые файлы приходят в `files[]`
ссылками download_url.

## 4. Листы согласования: подписанты из Doc-V (режим снимка)

Если первая запись реестра несёт объект `signers`, шлюз пишет подписи
ГОТОВЫМИ ЗНАЧЕНИЯМИ вместо ID + VLOOKUP: реестр перестаёт меняться
задним числом при правках листа СПР_ПОДПИСАНТОВ, а состав подписантов
целиком определяет Doc-V. Без `signers` работает прежний режим
(матрица approvers.yaml).

Формат (внутри каждой записи `request[]`, читается из первой записи
группы компания+объект; для реестра предстоящих платежей — из первой
записи реестра):

```json
"signers": {
  "soglasovano":  {"fio": "Аманов Б.Ш.",  "position": "Генеральный директор", "company": "ТОО «Шар-Кұрылыс»"},
  "utverzhdayu":  {"fio": "Акшалов Т.М.", "position": "Директор",             "company": "ТОО \"СМУ Аргон\""},
  "coordinators": [
    {"fio": "Абдрахманова Х.М.", "position": "Главный бухгалтер", "company": "ТОО «Шар-Кұрылыс»"},
    {"fio": "Бекмуратов Е.И.",   "position": "Начальник ЮО", "mark": "СОГЛАСОВАНО"}
  ]
}
```

- `soglasovano` — левый верхний блок («СОГЛАСОВАНО:»), `utverzhdayu` —
  правый («УТВЕРЖДАЮ»); отсутствующий блок остаётся пустым, заголовок
  не печатается.
- `coordinators` — подписи под таблицей по порядку; `mark` даёт
  строку-заголовок над подписью (прежнее поведение «СОГЛАСОВАНО» перед
  юристом).
- Реестр предстоящих платежей читает только `coordinators`
  (должность + ФИО построчно).

На стороне Doc-V объект собирается на точке «## Отправка данных»:
выборки по справочнику Структура (руководители компании и отделов по
полям должности), затем «Запись» складывает JSON в поле, которое уже
уходит в теле HTTP-запроса. Актуальность гарантирована моментом
формирования реестра.

### Файл одним действием (без второго запроса)

В «HTTP-запросе» галка «загрузить файл» есть только у GET, а тело
JSON — только у POST. Чтобы не делать два действия, шлюз принимает
данные прямо в адресе и отвечает **самим файлом**:

```
GET http://192.168.30.19:25353/render/typst/contract_card?data={{JSON поле}}
GET http://192.168.30.19:25353/render/registry/inner?data={{JSON поле}}
```

Настройка действия: метод **GET**, URL шаблоном с подстановкой
JSON-поля в параметр `data`, переключатель **«Кодировка параметров в
application/x-www-form-urlencoded» включён** (иначе кавычки и кириллица
поедут), заголовок Authorization как обычно, переключатель **«загрузить
файл» включён**, результат — файловое поле с методом добавления файла.
Второе действие и разбор `download_url` не нужны.

Длина адреса: проверено до 37 000 знаков (200 согласований) — работает;
реальная карточка договора с девятью визами укладывается в ~4 600
знаков. Если данных станет заметно больше, вернитесь к паре запросов
POST + GET, как в реестре платежей.

Тем, кто ходит POST-ом и хочет файл в ответе вместо ссылки, достаточно
добавить `?direct=1`.

Отдельная печатная форма карточки договора:
`POST /render/typst/contract_card` (бывш. list_soglasovaniya —
переименован, ваши правки перенесены автоматически) — формат данных в
шапке самого шаблона (правится в /ui, вкладка «Шаблоны»). Оформление — по дизайн-системе «Приёмка ERP SHARK». Организация
передаётся объектом: `"organization": {"name": …, "code": "СМ",
"blank_filepath": "blank_sm.png", "top_margin": 4.2}`. Бланк ищется в
«Картинках» шлюза по имени файла (путь режется до имени, ключ
`blank_file_name` тоже принимается); `top_margin` — отступ в см под
шапку бланка. Коды поля «Виза» печатаются подписями: 1 — Согласен,
2 — Подписан, −1 — Не согласен, −2 — Не подписан; незнакомый код
выводится как есть. Строки группируются по первой колонке «Таблицы
решения» с подписью из `stage_label` (по умолчанию «ЭТАП», пустая
строка отключает группировку). Поле `qr` (адрес карточки документа)
шлюз сам превращает в QR-код;
код подлинности и время формирования шлюз добавляет автоматически
(GW_VERIFY_SECRET в .env). Если сервис уже запускался со старой версией
шаблона, новая из файлов сама не заедет: удалите шаблон в /ui →
«Шаблоны» и перезапустите юнит — засев подтянет свежий файл.

### Фирменные бланки

Печатная форма умеет ложиться на фирменный бланк компании: PNG бланка
подкладывается фоном всей страницы, текст печатается поверх между
шапкой и нижней лентой. Подготовка (раз на компанию):

1. Загрузите PDF или DOCX бланка на страницу «Файлы» в /ui.
2. Запустите операцию blank_to_png (страница «Операции») — получите
   blank.png первой страницы (DOCX-вариант требует libreoffice на
   сервере, PDF конвертируется всегда).

   ВАЖНО про DOCX: LibreOffice воспроизводит вёрстку Word близко, но не
   на 100% — плавающие текстбоксы и WordArt могут съехать на строку.
   Эталонный путь: открыть бланк в самом Word на любой офисной машине,
   «Сохранить как PDF», и конвертировать уже PDF — растеризация PDF
   ничего не искажает. Если PDF взять негде, поставьте на сервер
   метрически совместимые шрифты (`apt install ttf-mscorefonts-installer
   fonts-liberation && fc-cache -f`) — чаще всего смещение уходит.
3. Скачайте PNG и загрузите его в «Картинки» вкладки «Шаблоны» под
   именем по договорённости: `blank_<код>.png` (blank_shar.png).
4. В данные листа кладите `"org": {"blank": "blank_shar.png",
   "top_margin": 4.2}` — отступ в сантиметрах под шапку конкретного
   бланка подберите пробным рендером.

### Справочники соответствий (расшифровка UID)

Сериализация табличных полей отдаёт ссылки сырыми UID-ами
(«approved_by» в листе согласования). Шлюз расшифровывает их своими
справочниками: `POST /directory/structura` и `POST /directory/dolzhnosti`
(токен docv), тело — `{"items": [{"uid": "…", "display_name": "…", "position": "…",
"department": "…"}]}` (display_name нормализуется в name; position
текстом покрывает и должность в разборе — отдельный справочник
должностей не обязателен); каждый POST замещает справочник целиком. Рендер подкладывает справочники
каждому шаблону входом `sys.inputs.dir`; неизвестный UID печатается
укороченным («8 знаков…?»), коды визы (1/-1/2/-2) и ISO-даты шаблон
переводит сам.

Минимизация: выгружайте только участников согласований (фильтр цикла
по ролям «Подписант»/«Согласующий» Структуры) и только пары uid+name —
ничего сверх. Справочник, не обновлявшийся 30 дней, шлюз вычищает сам;
файл базы — с правами 600.

Выгрузка из Doc-V — точка на планировщике (раз в сутки) или кнопка
в НАСТРОЙКАХ: цикл replay по записям Структуры → add_key с arrayAction
собирает [{uid, name}] (uid — сырое значение ссылки, name —
отображаемое имя) → «HTTP-запрос» POST на /directory/structura;
вторая такая же цепочка по Должностям. Проверка: GET /directory
показывает счётчики.

## 5. Шаблоны Typst

Шаблоны живут в базе шлюза и правятся в /ui → «Шаблоны»: редактор,
история 20 версий с откатом, пробный рендер, картинки (логотипы,
печати) — в шаблоне `#image("assets/имя.png")`. Файлы в repo
templates/typst/ — только начальный засев: новый файл импортируется
при старте, дальше источник правды — база.
